# Benchmarks

This page shows what TRAM's pipelines and components cost, to help with sizing deployments and choosing configurations. The tables are generated by `tools/benchreport` from the benchmarks in the repository; see [Regenerating](#regenerating).

Absolute numbers depend on the machine, its load and the network to NATS, so treat them as an indication for the environment below. Costs per record and the ratios between configurations carry over much better than throughput figures.

---

## How to Read the Numbers

- **Record:** a log record, metric data point or span. **Event:** one OTLP request or one broker message, carrying one or more records.
- **CPU per record:** CPU time (user and system) of the whole process, divided by the records processed. It includes garbage collection. For the OTLP scenarios it also includes the HTTP client that generates the load in the same process, so it is an upper bound. NATS runs in a container, and its CPU time is not included.
- **Small events overstate CPU.** With 1 record per event, the process mostly waits for HTTP and NATS round trips, and the Go runtime uses CPU between those short requests as well. These rows therefore show far more CPU per record than the work itself costs (compare the per-event costs under [Where the Time Goes](#where-the-time-goes)). Use the rows with 100 or 1,000 records for sizing; treat single-record rows as a pessimistic bound
- **Records/s per core:** how many records one fully used CPU core can process, derived from the CPU per record. This is the figure for sizing, as TRAM is stateless and scales horizontally.
- **Records/s:** the throughput actually measured on this machine. It is also limited by the number of callers and by NATS.
- **Latency:** time from sending an OTLP request until TRAM answered it. TRAM answers once all sinks accepted the data, so it includes publishing to NATS.
- **Per record / per event (components):** wall time of one caller. For components that wait, such as sinks waiting for a broker's acknowledgement or a disk sync, it includes the wait.
- **CPU per record / per event (components):** CPU time of the whole process during the measurement, divided by the records or events. It is the cost to size with when TRAM, not the broker, is the limit. It includes the garbage collector, which runs on other cores, so it can exceed the wall time; it excludes the brokers in their containers.
- **Spread:** range of the runs relative to the median. Values above 10% are flagged with ⚠️ and are less reliable.

## Sizing

CPU needed for pure processing, from the CPU per record of the scenarios above. The unbatched row is a pessimistic bound, see [How to Read the Numbers](#how-to-read-the-numbers); the point it makes holds regardless: unbatched single-record events cost many times more than batched ones. Plan headroom on top, for load peaks, garbage collection and the network. Allocation rates are high (see Allocs per record), so pods also need memory headroom; set `GOMEMLIMIT` and resource requests accordingly.

Scaling out works because TRAM keeps no state between events, with two conditions:

- **Broker source:** set `durable`, so the pods share one consumer and split the messages. Without it, every pod receives every message
- **NATS server:** all pods publish to the same JetStream streams. A stream is written by one NATS node, so at very high load NATS, not TRAM, becomes the limit; spread the data over several streams

## Streams per Instance

The cost of processing data is shared by the replicas, but the cost of a stream itself is not: every replica that runs a stream holds its connections, goroutines and memory, and its broker sources keep asking the NATS server for messages even when there are none. This section measures that cost, so you can tell when to shard streams over several deployments with `--watch-namespace` or `--engine` (see [the operator documentation](internal/adapters/k8scrd/README.md#selecting-streams)) instead of running every stream on every replica.

`BenchmarkStreams` builds 10, 100 and 1,000 streams of one shape in one TRAM core and observes them for 10 seconds without data. Values are per stream, measured against the process before the streams were built:

- **Build:** time to create the stream through the core, including connecting to NATS
- **Heap:** live heap after a garbage collection. RSS is higher; see [Sizing](#sizing)
- **NATS connections:** client connections the NATS server sees. Every broker source and sink has its own
- **NATS messages/s, idle:** messages the NATS server receives from the idle stream, mostly the pull requests of the broker source, which renews its request every 5 seconds
- **Idle CPU:** CPU the process uses for the idle stream, as a share of one core

Idle CPU is shown for 1,000 streams only; for fewer streams it is below the noise of the process.

How to read it:

- **Memory limits the streams per replica first.** Most of a stream's heap are the buffers of its NATS connections. Plan the memory request of a replica from the streams it runs, not only from its data rate
- **Replicas multiply the load on NATS.** Doubling the replicas of a deployment that runs every stream doubles the connections and idle requests the NATS server handles, while each replica still holds all streams. Shard the streams when the per-replica heap or the NATS totals get too high, and scale replicas within a shard for the data rate
- **Workers cost only while messages are in flight.** A broker source has one pending pull request however many workers it has, and runs a goroutine per message being processed

## Tuning

- **Batch before the broker sink.** The sink waits for JetStream to acknowledge the messages of an event. With small events that round trip dominates; batching spreads it over many records. Compare `otlp-nats` with 1 and with 1,000 records per event
- **Batching needs concurrent callers.** Each caller of a `batch` stage waits for its batch to be delivered. With a single caller, batches never fill and every event waits for `timeout`; see `otlp-batch-nats` with 1 caller
- **Keep the number of subjects per event low.** The broker sink publishes one message per subject. It sends them all at once and waits for their acknowledgements together, so many subjects cost little time, but every message still costs CPU on TRAM and the NATS server
- **Give a broker source enough workers.** `workers` is the number of messages processed at the same time, so a `batch` stage after the source holds at most that many messages. The source acknowledges a message once its batch is delivered, so a source with a `batch` stage handles at most `workers / timeout` messages per second: 20 workers and a timeout of 1 s cap it at 20 messages/s per replica, however fast the sink is
- **Prefer resource-level CEL expressions.** They are evaluated once per resource instead of once per record when used in a `validation` stage; per record, CEL costs about as much as decoding the record
- **Many consumers filtering one stream make NATS the limit.** Each filtered consumer searches the stream for its next matching message. With hundreds of them on one stream, NATS spends its CPU on that search and, on slow storage, on reading blocks from disk; see [Load Test on Kubernetes](#load-test-on-kubernetes)
- **Prefer `retention: interest` for streams that only pass data on.** NATS removes a message once every consumer acknowledged it, so the stream stays small while consumers keep up and still holds the backlog of one that falls behind, up to `max_age`

## Load Test on Kubernetes

Unlike the tables above, this is a manual end-to-end test of one topology, not generated by `tools/benchreport`. It ran the tenant routing topology with production-shaped traffic on a managed Kubernetes cluster to see what one TRAM pod handles and where a complete system hits its limit.

What it shows:

- **TRAM needs about 0.32 cores per 100 requests/s, and its memory hardly grows with load.** About 450 MB of the heap are the 553 streams alone (see [Streams per Instance](#streams-per-instance)); load adds a few hundred MB. Scale TRAM on CPU
- **NATS sets the limit of the system, at about 650 to 700 requests/s.** NATS used only 2 of its 4 cores: half of its CPU went to the 500 link consumers searching `telemetry` for their next message, 15% to writing consumer state on acknowledgements. Publishes compete with that, so their latency jumps from 140 ms to 1.7 s. More TRAM replicas do not move this limit, as they share the same consumers
- **NATS needs fast storage when many consumers filter one stream.** On block storage with 500 IOPS, the same setup collapsed at 100 requests/s: NATS kept re-reading blocks from disk for the filtered consumers, publishes took up to 7 s, and NATS grew to its 8 GB memory limit. With 60,000 IOPS, 100 requests/s took 47 ms per publish
- **`retention: interest` made NATS' work lighter.** At 100 requests/s, the streams stayed at a few MB instead of 2.6 GB with `limits` and 5 minutes of retention; NATS publishes took 7 to 9 ms instead of 47 ms
- **The batch timeout limited the routers.** With 20 workers and a timeout of 1 s, each router handled at most 20 messages/s per replica, and a backlog built up at 400 requests/s; with 200 ms it did not

## Known Limits

- NATS ran in a container on the same machine. Over a real network, every acknowledgement takes longer, which affects small events and many subjects most
- The OTLP scenarios generate load from the same process and machine, which competes with TRAM for CPU
- The generated benchmarks measure one TRAM instance; they do not cover several pods sharing a NATS server. The fleet table under [Streams per Instance](#streams-per-instance) multiplies the per-stream costs instead, assuming the NATS server's cost grows linearly with connections and requests. [Load Test on Kubernetes](#load-test-on-kubernetes) measured one replica against a shared NATS server; scaling out to several replicas under load is not measured yet
- `BenchmarkStreams` measures idle streams. It does not measure how idle streams slow down a busy one, beyond the idle CPU they use

## Regenerating

The scenario and broker benchmarks need Docker or Podman, which run NATS, Kafka and ActiveMQ Artemis in containers; without them they are skipped and their rows show `n/a`. With Podman on macOS, point Testcontainers to the socket inside the Podman VM first:

```bash
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/run/podman/podman.sock
export TESTCONTAINERS_RYUK_CONTAINER_PRIVILEGED=true
```

Then run all benchmarks and update this page (takes about 25 minutes, of which the streams benchmarks take about 9):

```bash
go run ./tools/benchreport -raw bench.txt
```

The benchmarks run one package at a time, as parallel packages would distort each other. Keep the machine otherwise idle. To change only the text around the tables, regenerate from the saved output without measuring again:

```bash
go run ./tools/benchreport -input bench.txt
```

Flags: `-count` (runs per benchmark, default 3), `-scenario-benchtime` (default `1s`), `-component-benchtime` (default `300ms`), `-out` (default `BENCHMARK.md`).
