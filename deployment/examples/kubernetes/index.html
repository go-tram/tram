Kubernetes Examples¶

This directory contains Kubernetes YAML configurations for deploying TRAM streams in Kubernetes environments. Each example has a corresponding JSON configuration in the ../config/ directory with the same base filename.

Every example runs on the Engine demo from examples/engine.yaml: its spec.engineRefs names it. The OTLP examples listen on ports of their own, 4318 to 4327, which the Engine declares, so all examples can run on it at once.

Quick Start¶

Prerequisites¶

  • Kubernetes cluster
  • NATS server or OpenTelemetry Collector deployment (depending on the example)

Install the Manager and the Engine¶

From the repository root, with the Helm chart charts/tram, which installs the CRDs, the roles and the manager:

helm install tram charts/tram --namespace tram-system --create-namespace

# The Engine that runs the examples
kubectl apply -f examples/k8s/examples/engine.yaml
kubectl wait engine/demo --for=condition=Ready

Or without Helm, with the kustomization in manifests/: the CRDs in manifests/crds/, and the manager with its roles in manifests/tram-manager/, in the namespace tram-system. Apply it server-side, since the CRDs are too large for a client-side apply. From the repository it deploys the image latest; every GitHub Release has the same manifests with the release's image as tram.yaml:

kubectl apply --server-side -k manifests/
# or a release
kubectl apply --server-side -f https://github.com/go-tram/tram/releases/latest/download/tram.yaml

# The Engine that runs the examples
kubectl apply -f examples/k8s/examples/engine.yaml
kubectl wait engine/demo --for=condition=Ready

Deploy a Stream¶

# Deploy a basic OTLP forwarding stream
kubectl apply -f examples/k8s/examples/otlp_basic.yaml

# Check the stream: labeled engine.tram.io/demo and mounted (column MOUNTED)
kubectl get streams --show-labels
kubectl get engines

# Or deploy every example at once, with the Engine
kubectl apply -f examples/k8s/examples/

Layout¶

  • examples/engine.yaml: the Engine demo, which runs every example
  • examples/: the Stream examples below

Available Examples¶

Basic OTLP Examples¶

These examples demonstrate using the OTLP sink in TRAM for various use cases.

otlp_basic.yaml¶

Purpose: Basic OTLP to OTLP forwarding - Receives OTLP data on port 4318 - Forwards to a central OTLP collector - No processing stages - JSON version: ../config/otlp_basic.json

otlp_tenant_routing.yaml¶

Purpose: Route the data of several tenants by a header an ingress per tenant sets - Receives OTLP on ports 4331 (HTTP) and 4332 (gRPC); the ingress of each tenant sets X-Tram-Router, which the source copies into the resource attribute tram.router.id - Rejects requests without a valid router ID before the batch, then routes each record to router.<router-id>.<signal> in NATS - Restrict the ports to the ingress controller with a NetworkPolicy, so no one sends with a header of their choice - JSON version: ../config/otlp_tenant_routing.json

otlp_grpc.yaml¶

Purpose: OTLP over gRPC and HTTP into one stream - Receives OTLP/gRPC on port 4317 and OTLP/HTTP on port 4329; the example Engine lists both ports, so its Service exposes them - Forwards both to a central OTLP collector - JSON version: ../config/otlp_grpc.json

otlp_debug.yaml¶

Purpose: OTLP into the debug sink, to see what reaches an Engine - Receives OTLP data on port 4327 - Logs every record it receives; see them with stern -l tram.io/engine=demo - No JSON version

otlp_secure.yaml¶

Purpose: Secure OTLP forwarding with authentication - Receives OTLP data on port 4321 - HTTPS endpoint - Bearer token authentication - Custom headers for metadata - JSON version: ../config/otlp_secure.json

otlp_insecure_dev.yaml¶

Purpose: Development configuration with insecure TLS - HTTPS endpoint with invalid certificate acceptance - Useful for local development and testing - Generator source for testing - JSON version: ../config/otlp_insecure_dev.json

Processing Pipeline Examples¶

otlp_batch.yaml¶

Purpose: High-throughput OTLP forwarding with batching - Receives OTLP data on port 4319 - Batches events for better throughput - 1000 records max per batch - 200ms timeout for batch flush - JSON version: ../config/otlp_batch.json

otlp_with_filters.yaml¶

Purpose: OTLP forwarding with CEL filtering - Receives OTLP data on port 4322 - Filters logs based on customer attribute - Sends filtered data to customer-specific endpoint - JSON version: ../config/otlp_with_filters.json

otlp_with_transform.yaml¶

Purpose: Normalize attributes with the transform stage - Receives OTLP data on port 4330 - Derives deployment.environment on the resource, deletes password, renames user to user.name, truncates note and lowercases the severity into level - JSON version with test cases: ../tests/otlp_with_transform.json; Stream resources have no tests field, so the tests live in the JSON file

otlp_with_validation.yaml¶

Purpose: Validated OTLP forwarding with CEL validation - Receives OTLP data on port 4323 - Validates that all resources have service.name attribute - Rejects invalid data - JSON version: ../config/otlp_with_validation.json

Multi-Sink Examples¶

otlp_multi_sink.yaml¶

Purpose: Multiple OTLP sinks from a single source (fan-out) - Receives OTLP data on port 4320 - Splits data into different streams using filters - Sends error/warn logs to one endpoint - Sends all data to another endpoint - JSON version: ../config/otlp_multi_sink.json

Integration Examples¶

otlp_nats_bridge.yaml¶

Purpose: Bridges NATS JetStream to OTLP HTTP - Consumes OTLP logs from NATS JetStream with the broker source - Uses durable consumer with multiple workers - Batches messages for efficiency - Forwards to central OTLP collector - JSON version: ../config/otlp_nats_bridge.json

otlp_benchmark.yaml¶

Purpose: High-performance benchmark configuration - Generator source for load testing - Large batch sizes (8192 records) - Short batch timeout (100ms) - JSON version: ../config/otlp_benchmark.json

Benchmark Configurations¶

These configurations match the exact scenarios used in the TRAM benchmarks (see BENCHMARK.md). They demonstrate pipelines with OTLP sources, various processing stages, and broker sinks over NATS. The JetStream streams have to exist, since TRAM creates none.

benchmark_otlp_nats.yaml¶

Purpose: Exact configuration for the otlp-nats benchmark scenario: OTLP → NATS - Receives OTLP data on port 4324 - Matches the official benchmark configuration - JSON version: ../config/benchmark_otlp_nats.json

benchmark_otlp_batch_nats.yaml¶

Purpose: Exact configuration for the otlp-batch-nats benchmark scenario: OTLP → batch → NATS - Receives OTLP data on port 4325 - Uses batch with max_records: 1000, timeout: "10ms" as in benchmarks - JSON version: ../config/benchmark_otlp_batch_nats.json

benchmark_otlp_split_nats.yaml¶

Purpose: Exact configuration for the otlp-split-nats benchmark scenario: OTLP → 2 × filter → 2 × NATS - Receives OTLP data on port 4326 - Splits into team-0 and other teams as specified in benchmarks - JSON version: ../config/benchmark_otlp_split_nats.json

benchmark_nats_filter_nats.yaml¶

Purpose: Exact configuration for the nats-filter-nats benchmark scenario: NATS → filter → NATS - Uses durable consumer with workers as in benchmarks - JSON version: ../config/benchmark_nats_filter_nats.json

Configuration Reference¶

Service Discovery¶

For production environments, consider using Kubernetes service discovery:

spec:
  sinks:
    - type: otlp
      name: my_sink
      from: my_source
      spec:
        url: "http://otel-collector-service.namespace.svc.cluster.local:4318"

NATS Configuration¶

For NATS-based examples, configure the NATS driver of the broker source. The JetStream stream that holds the subject has to exist; TRAM creates none:

source:
  type: broker
  name: my_source
  spec:
    driver: nats
    signal: logs
    workers: 8
    nats:
      url: "nats://nats-server:4222"
      subject: "my-stream.logs"
      durable: "my-durable-consumer"

Secrets¶

Keep sensitive values in a Secret in the namespace of the Stream and refer to it; the value replaces the whole field, see Secrets:

spec:
  sinks:
    - type: otlp
      name: secure_sink
      from: my_source
      spec:
        url: "https://otel-collector:443"
        headers:
          Authorization:
            valueFrom:
              secretKeyRef:
                name: otel-secrets
                key: authorization

Deploy with: 

kubectl create secret generic otel-secrets --from-literal=authorization="Bearer your-api-key-here"
kubectl apply -f your-stream.yaml

Resource Management¶

Streams run on the instances of an Engine, so resources and scaling are set on the Engine, for all of its Streams.

CPU/Memory Requests¶

apiVersion: io.tram.core/v1alpha1
kind: Engine
metadata:
  name: high-volume
spec:
  resources:
    requests:
      cpu: 500m
      memory: 512Mi
    limits:
      memory: 1Gi

Horizontal Pod Autoscaling¶

The manager creates the HorizontalPodAutoscaler of an Engine:

apiVersion: io.tram.core/v1alpha1
kind: Engine
metadata:
  name: high-volume
spec:
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 10
    targetCPUUtilizationPercentage: 70

Integration Patterns¶

OpenTelemetry Collector Integration¶

The most common use case is forwarding to an OpenTelemetry Collector:

spec:
  sinks:
    - type: otlp
      name: otel_collector_sink
      from: source_or_stage
      spec:
        url: "http://otel-collector:4318"

NATS JetStream Integration¶

For NATS-based pipelines, use the broker source and sink with the NATS driver. Set up the streams first, e.g. nats stream add input --subjects 'input.>' --defaults and nats stream add output --subjects 'output.>' --defaults:

source:
  type: broker
  name: nats_source
  spec:
    driver: nats
    signal: logs
    workers: 4
    nats:
      url: "nats://nats-server:4222"
      subject: "input.logs"
      durable: "tram-consumer"

sinks:
  - type: broker
    name: nats_sink
    from: nats_source
    spec:
      driver: nats
      nats:
        url: "nats://nats-server:4222"
      destination:
        logs: "'output.logs'"

Several Engines¶

Which instances run a Stream is decided by spec.engineRefs, not by labels. To run streams in different places, e.g. per zone, node pool or team, create an Engine for each and name the Engines a Stream should run on:

apiVersion: io.tram.core/v1
kind: Stream
metadata:
  name: my-stream
spec:
  engineRefs:
    - name: zone-a
    - name: zone-b
  # ...

Canary¶

To try a new configuration or TRAM version on part of the traffic, run it on an Engine of its own, e.g. demo-canary with another spec.image, as a Stream with another name and engineRefs: [{name: demo-canary}]. Then send a share of the traffic to that Engine's Service, e.g. from the load balancer or the senders, and remove the Engine or the Stream when you are done.

Monitoring and Observability¶

Health Checks¶

Check stream health: 

kubectl get stream my-stream -o yaml
kubectl describe stream my-stream

Logs¶

View the logs of the instances of an Engine, which run its streams: 

kubectl logs -l tram.io/engine=demo --prefix

Metrics¶

Every instance serves Prometheus metrics on /metrics of its HTTP API, which the Engine's Service exposes as the port http: 

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: tram-examples
spec:
  selector:
    matchLabels:
      tram.io/engine: demo
  endpoints:
    - port: http
      path: /metrics
      interval: 30s

Performance Optimization¶

Connection Pooling¶

The OTLP sink uses HTTP connection pooling by default: - Max idle connections: 100 - Idle connection timeout: 90 seconds - Max idle connections per host: 100

Batch Size Tuning¶

Adjust batch sizes based on your workload:

stages:
  - type: batch
    name: batch
    from: source
    spec:
      max_records: 5000    # Increase for high throughput
      timeout: "500ms"    # Increase to allow larger batches

Timeout Configuration¶

Set appropriate timeouts:

sinks:
  - type: otlp
    name: my_sink
    from: batch
    spec:
      url: "http://collector:4318"
      timeout: "60s"  # Longer timeout for large batches

Troubleshooting¶

Connection Issues¶

Check connectivity to your endpoints. The TRAM image has no shell, so use a temporary pod in the namespace of the Engine: 

kubectl run curl --rm -it --restart=Never --image=curlimages/curl -- curl -v http://otel-collector:4318/v1/logs

Certificate Issues¶

For HTTPS endpoints with self-signed certificates:

sinks:
  - type: otlp
    name: insecure_sink
    from: source
    spec:
      url: "https://collector:443"
      insecure: true  # Skip certificate validation

Or properly configure certificates in your cluster.

Authentication Issues¶

Verify that the secrets a Stream refers to exist; a missing secret or key keeps the stream from starting and sets status.mounted to false: 

kubectl get secret otel-secrets -o jsonpath='{.data}'
kubectl get stream my-stream -o jsonpath='{.status}'

Security Best Practices¶

  1. Use HTTPS: Always use HTTPS in production for external endpoints
  2. TLS Certificates: Use proper TLS certificates, not insecure: true
  3. Secrets Management: Use Kubernetes Secrets for sensitive data
  4. Network Policies: Restrict access to your TRAM streams
  5. RBAC: Use appropriate RBAC roles for the TRAM operator

Example NetworkPolicy: 

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: tram-allow-endpoints
spec:
  podSelector:
    matchLabels:
      tram.io/engine: demo
  policyTypes:
    - Egress
  egress:
    - to:
        - podSelector:
            matchLabels:
              app: otel-collector
      ports:
        - protocol: TCP
          port: 4318
    - to:
        - podSelector:
            matchLabels:
              app: nats
      ports:
        - protocol: TCP
          port: 4222
